# Formats, layouts, and PDF plan

Planning note for the AutoCAD-2027-like LibreCAD fork on macOS arm64, with a Windows-style AutoCAD interface adapted to macOS and 2D drafting first. Repository baseline inspected: `628a1ba845931a37b8d745a8ad08d4731615812c`. Scope is DWG/DXF exchange, genuine model/paper-space layouts, and publishing PDF sheets. The initial “dxg” spelling is resolved as DXF. No code changes are included here.

## Product contract

Treat file-format support as an end-to-end promise, not a parser dispatch table. For each advertised feature and source version, distinguish these observable levels:

1. **Recognized:** the file/version or record name is identified.
2. **Decoded:** fields are parsed with validated lengths, owners, and references.
3. **Retained:** the application document owns the semantic data after import.
4. **Rendered/edited:** the feature appears and behaves correctly in the editor and plot path.
5. **Round-tripped:** save/reopen preserves the feature, relations, and appearance in the declared compatibility range.

An unsupported feature must produce a visible, actionable import/save report. Never silently discard it, convert it to empty geometry, or overwrite the only source copy after a lossy save. Keep unknown or unsupported records in an opaque preservation layer when handles, owners, and source-version conditions permit; warn when edits invalidate that preservation or a version downgrade makes replay unsafe. Before saving over the source, write to a temporary sibling, verify that it can be reopened and that critical records survive, then atomically replace only after success. Offer Save As / backup and an explicit loss report for any conversion with known losses.

The file version is a separate choice from the product release name. Autodesk’s current compatibility table says AutoCAD 2018 through AutoCAD 2027 use the AutoCAD 2018 DWG format; Autodesk’s 2027 customization note independently says 2027 continues the 2018 drawing format. Thus the first modern target is **AC1032 (AutoCAD 2018 DWG family)**, validated against actual AutoCAD 2027-generated and AutoCAD 2027-opened files; do not invent an “AutoCAD 2027 DWG version.” The fork’s existing version inventory maps AC1032 to 2018/2019/2020 and marks the reader/writer paths as static-entrypoint only, with fixture gates still blocked. Update the release-family table with Autodesk’s 2027 compatibility evidence while retaining AC1032 as the on-disk version code. [Autodesk: drawing file format compatibility](https://help.autodesk.com/view/ACADWEB/ENU/?caas=caas%2Fsfdcarticles%2Fsfdcarticles%2FAutoCAD-drawing-file-format.html), [Autodesk Developer Blog: AutoCAD 2027 interoperability](https://blog.autodesk.io/autocad-2027-interoperability-for-customization/)

## Baseline and concrete gap

The fork compiles bundled libdxfrw into the app and currently defines `DWGSUPPORT` for the main library and filter compile-check target (`CMakeLists.txt:388, 2227-2269`). The existing filter adapter is [rs_filterdxfrw.cpp](../../librecad/src/lib/filters/rs_filterdxfrw.cpp): `addLayout` stores the parsed `DRW_Layout` record and initializes the active handle (lines 10766-10785); `addBlock` maps model space to `RS_Graphic` but sends special `*Paper_Space...` blocks to `m_dummyContainer` (4724-4775); `setBlock` then routes their entities to that sink (5008-5019). So a DXF/DWG parser may decode an entity while the editor does not retain or display it. Fix the entity ownership path before claiming paper-space display or editing.

There is also an XREF embed path: import detects XREF block flags and can resolve the stored path and copy model-space entities and block definitions into a namespaced host block (`rs_filterdxfrw.cpp:4747-4755, 4836-5005`). Treat this as bind/embed assistance, not a full live XREF reference manager with independent attach/reload/unload, path state, and dependency-aware editing. Preserve and report unresolved references instead of representing them as valid empty content.

There is real layout metadata groundwork. `LC_DwgAdvancedMetadata::LayoutRecord` carries the LAYOUT object’s plot-settings prefix, page dimensions, margins, plot type/scale, name, order, UCS, layout flags, and viewport handle references (`lc_dwgadvancedmetadata.h:2729-2800`); the filter and writer have layout-specific encode paths. `RS_Graphic` exposes a read-only layout view, active handle, and per-layout margins (`rs_graphic.h:95-145`, `rs_graphic.cpp:785-860`). The tab bar displays Model plus sorted paper-space layout names and changes only the handle; its own header explicitly says no rendering swap is performed (`lc_layouttabbar.h:37-53`, `lc_layouttabbar.cpp:110-175`). `QC_MDIWindow` constructs the tab bar and binds the graphic but does not connect its `tabClicked` signal to a view change (`qc_mdiwindow.cpp:175-194`; repository search finds only the signal declaration/emission); the click currently updates active metadata and emits an unconsumed signal (`lc_layouttabbar.cpp:165-175`, `rs_graphic.cpp:798-804`). This means “layout tabs exist” is true, but “paper space works” is not yet true.

Likewise, PDF export exists but is not layout publishing. The command-line `PdfPrintLoop` opens one graphic and creates one PDF per source; in combined mode it appends the tiled-model pages from each input, so one source may yield multiple pages (`pdf_print_loop.cpp:47-107, 110-193, 267-335`). `touchGraphic` applies one `LC_PlotSettings` and fit/center options (`216-237`); `drawGraphic` builds one `LC_GraphicViewport` over the whole graphic and tiles that model view by the plot page counts (`267-335`). For combined output, the first opened drawing supplies the printer/page setup for every drawing (152-156). GUI print uses the document singleton `LC_PlotSettings` for paper format/size/scale and only consults the active layout’s margins (`lc_printing.cpp:119-197, 200-243`; `rs_graphic.cpp:842-860`). It does not select a layout’s own page setup, render paper-space entities plus model-space viewport windows, or publish every selected layout. Autodesk defines a layout as a sheet combining paper-space border/notes and one or more model-space viewports, each layout having its own page setup; publishing sends selected layouts to PDF or plotters. [About plotting and layouts](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-Core/files/GUID-2DB9EB8C-767C-4C91-B0A3-FFFEC4C5863A.htm), [named page setups](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-Core/files/GUID-2C5C9DE4-0740-4D7F-A781-745A04F588B0.htm), [publish multiple layouts](https://help.autodesk.com/cloudhelp/2027/ENU/AutoCAD-Core/files/GUID-556BF24C-3996-4F6B-87AC-2BAC0FD9EE21.htm).

The generated repo evidence must remain qualified as static readiness evidence. [DWG_VERSION_SUPPORT_STATUS.md](../../libraries/libdxfrw/DWG_VERSION_SUPPORT_STATUS.md) (lines 5-7) says dispatch/entrypoint rows need positive and negative fixture proof; its AC1032 row has `dwgReader32` / `dwgWriter32` but is only `V2/V4-static-entrypoint` (26-46). [DWG_DXF_WRITER_SUPPORT_STATUS.md](../../libraries/libdxfrw/DWG_DXF_WRITER_SUPPORT_STATUS.md) (5-7) lists one native-typed container path and 208 raw-replay routes per supported DWG version, but requires fixtures and oracle gates before promotion (16-36). The generated [gap report](../../docs/gap-report.md) (1-7, 16-38, 57-70) likewise labels AC1032 static and lists feature gaps as fixture-blocked. Passing a low-level read/write or compiler test is not proof that an edited LibreCAD document retained, displayed, plotted, and round-tripped the content.

## Compatibility contract and scope

Adopt an explicit compatibility matrix before implementing more format code. Each matrix row should include file version code, reader level, writer level, supported entity/object families, tested coordinate/units behavior, layout and viewport subset, external dependencies, loss behavior, and fixture/oracle status. Baseline targets:

- **DXF:** ASCII and binary DXF at the declared R12/R2000/2004/2007/2010/2013/2018 generations, with exact import/export behavior per generation. Keep broad format recognition separate from support for an entity/object family. Preserve tables, blocks, layers, styles, XDATA/EED, dictionaries, owner/handle relations, and unknown records where feasible.
- **DWG read:** begin with AC1032 read-only import for ordinary 2D geometry, layers, blocks/inserts, text/dimensions/hatches, and supported layout/page metadata; then backfill older versions according to fixture-backed demand. A future file opening must not imply editable semantics for proxies or unsupported objects.
- **DWG write:** staged Save As first, starting with AC1032 output for the explicitly typed and validated subset. Expand only version/family rows that pass a same-version reopen and external-reader check. Do not promise full AutoCAD round-trip until key ACAD proxy/custom classes, associative/dynamic objects, xrefs, underlays, fonts, and application metadata have an explicit preserve/convert/drop policy and loss report.
- **DXF is the editable interchange fallback.** A DWG read-only path may still have product value, but DWG Save must be disabled or precisely constrained until its row passes the gate. Document that a round-trip can alter AutoCAD-only semantics even where visible geometry is retained.

Resolve input/output unit conversion and coordinate contracts at the import boundary: `$INSUNITS` / block insertion units, entity and block coordinate systems, OCS/ECS, extrusion, UCS, WCS, model extents, elevation, and paper units. Use double precision internally; never rescale stored geometry just to match current UI units. For mirrored/rotated/nonuniform INSERTs and nested blocks, test transformations and attributes. Keep format-native entities when editing is supported; use proxy/opaque records or a clearly identified display-only proxy graphic when it is not. A proxy graphic is a visualization fallback, not editable entity data.

## Document model and ownership

Add true layouts to the application’s document model rather than treating tabs as labels. Keep an explicit Model layout plus ordered paper layouts. Each layout owns its paper-space entity container/block-record handle, printable page definition and units, margins, orientation, plot area/type, scale or fit policy, plot style/table reference, named page setup, and plot device/media reference. Multiple named page setups may be shared or attached per sheet. Retain existing `LayoutRecord` metadata and evolve it behind typed document APIs; avoid a second conflicting copy of fields already stored there.

Represent each layout viewport as a first-class viewport entity owned by the paper-space container. Store its paper-space boundary/clip path, model view center/target and view height, twist/UCS, view direction where applicable, custom scale, lock state, frozen layers and per-viewport layer overrides. Support rectangular clips first; preserve unsupported polygonal/nonrectangular clips opaquely with a visible warning. Do not confuse the global Model-space `VPORT` view table or DWG viewport entity headers with paper-space viewport entities (`VIEWPORT`) that connect a layout sheet to a model view. Lay out these relations using validated handles and owners, with orphan/duplicate/cycle diagnostics.

Keep model-space geometry in the model owner and paper annotations/borders in each layout owner. Do not synthesize a fake “paper space block” into the general block insertion palette. Layout switching selects a scene composed of the paper container and viewport scenes; each viewport renders the shared model scene through its own transform, clip, and layer filter. The rendering/selection API must keep viewport object selection distinct from selecting model geometry through an activated viewport. An explicit current context (paper space, or a particular active viewport) is required for edit, pan, zoom, snapping, and status-bar scale behavior.

Persist document edits through the existing ownership, undo, dirty-state, and serialization systems. Layout creation, deletion, rename/reorder, page setup changes, viewport creation/transform/clip/scale/lock, and per-viewport layer overrides must each be atomic undo transactions. Undo/redo should restore the selected layout/viewport context and render state; active tab selection alone may remain a view preference if product behavior warrants it, but persisted drawing state and dirty tracking must be deterministic. `RS_Graphic::setActiveLayoutHandle` currently marks modified on change (`rs_graphic.cpp:798-804`), while `setLayoutMargins` mutates metadata and marks dirty (`806-839`); make the UI consume mutation methods rather than mutating raw metadata, then integrate them with undo. Add import/save/reopen tests that assert ownership of every paper-space entity and viewport reference.

## PDF and plot architecture

Create one shared sheet-rendering/publish service for GUI print preview, GUI PDF export, command-line PDF conversion, and future batch publishing. Input is a document plus an ordered list of sheets (layout IDs, optionally Model) and per-sheet page setup overrides. Output is a PDF page for each initialized selected layout with deterministic sheet order, page size/orientation, printable margins, vector geometry and text, lineweights/linetypes/colors/plot styles, and diagnostics. A single-layout export and multi-layout publish should call the same renderer. Keep the existing tiled-model print mode as a compatibility option for workflows that intentionally create several pages from model space.

For each selected layout, render the paper-space container once, then each model-space viewport clipped to its exact paper boundary and transformed at its saved scale; apply per-viewport layer freezes/overrides before drawing. Respect sheet-specific page setup, units, plot window/type, rotation, named page setup and the chosen device profile. A page setup that references an unavailable printer/media should map to an explicit fallback only after the user sees the substituted paper and diagnostics. Uninitialized layouts are skipped with a report or require an override; never silently produce a blank/default-sized sheet.

Keep PDF output vector based for CAD strokes and text whenever supported by Qt’s PDF engine. Verify glyph substitution, font embedding/subsetting, Unicode/RTL text, SHX-like CAD fonts, line dash phase, joins/caps, clipping, transparency, raster underlays and dimensions at actual target scales. Add font discovery/substitution UI and a per-export report for missing fonts, xrefs, plot styles, underlays and proxies; optionally offer embed/outline text subject to font license and fidelity. Compare generated PDF geometry/page boxes to curated reference plots by rasterized pixel/edge tolerances and extracted vector/text checks. PDF fidelity is its own acceptance gate; successful PDF creation proves only that a file was written.

## Suggested phases and gates

| Phase | Deliverable | Acceptance gate |
| --- | --- | --- |
| F0 — format truth | Version/entity capability matrix and loss taxonomy; fixture manifest pairing each known feature with source/oracle and expected diagnostics. | Each claim says recognized, decoded, retained, rendered, round-trip, or unsupported; no claim rests on dispatch alone. Record baseline fixtures from AutoCAD 2027 and independent DXF/DWG readers. |
| F1 — safe import and save | AC1032 and selected DXF read-only/round-trip subset; robust source-version detection, unit/coordinate normalization policy, opaque metadata retention, staged Save As, preflight loss report. | Malformed/truncated inputs fail safely; same-version fixtures reopen in LibreCAD and AutoCAD/ODA/LibreDWG as configured; unknown objects survive untouched saves where safe; edit-invalidated raw payloads are reported. No silent source overwrite or unannounced loss. |
| F2 — layouts as owned documents | Paper-space containers with import routing fixed; Model/ordered paper layouts in the scene/UI; layout-aware undo, dirty tracking, persistence, and selection. | Fixture with two paper layouts and both paper/model content shows correct content for each after tab switching and save/reopen; no paper-space entities go to dummy/discard sinks; undo/redo and reorder/rename/delete remain coherent. |
| F3 — viewport scenes | First rectangular viewport support, position, twist, scale, lock, clipping and viewport-frozen layers; preserve unsupported clip types raw. | Multiple viewports on one sheet show distinct scales/areas and per-viewport layers without changing global model layer states; clipping and pan/zoom lock behave; save/reopen in target AutoCAD preserves the view. |
| F4 — plotting and PDF publish | Shared per-sheet renderer, preview, single-sheet PDF and ordered multi-layout PDF; setup/device overrides and loss/font/dependency report. | Two-layout mixed-size/orientation fixture yields exactly two ordered pages with correct viewport transforms, margins, lineweights, text and dimensions; GUI and CLI output agree; model tiling remains independently testable. |
| F5 — compatibility expansion | Add DWG writer/editable entity families and DXF version coverage from ranked fixture demand. | Each version/family promotion requires positive and negative fixture, semantic readback, external-reader open/audit, visual comparison, and a documented downgrade/drop contract; release notes state tested limits. |

## Test corpus and release evidence

Build a redistributable, provenance-tracked corpus (or locally generated fixtures where source licenses restrict distribution) covering: multiple layouts with nontrivial tab order; paper entities and dimensions; multiple clipped viewports with different scales, twist and frozen layers; page setups of mixed size/orientation; inches/mm and nonzero UCS/OCS; nested blocks and attributes; Unicode and RTL; missing and present fonts; relative/absolute xrefs; raster/PDF underlays; proxy/custom entities; unsupported plot styles; empty/uninitialized layouts; corrupted owners/handles; AC1032 files made by AutoCAD 2027. Record source application/version, expected semantic inventory, expected loss warnings, and visual reference PDFs.

Run four distinct oracles: (1) application-level semantic inventory before and after save/reopen; (2) independent parser/auditor (ODA/AutoCAD where licensed, LibreDWG where useful, ezdxf for DXF); (3) visual canvas/preview/PDF comparison; (4) malformed-input and save-failure tests proving cleanup and source protection. A fixture's license and availability must be recorded. For supported text, compare both Unicode content and placement/shape; for layout, compare layout count/name/order, paper parameters, viewport transforms, clipping, and per-viewport layer rules. PDF acceptance includes page count/order/size and visual/text checks.

## DWG backend options and open checks

As of 2026-10-11, the practical choices differ in integration, platform, licensing, and writer maturity. Use these as candidates for the same fixture-backed prototype, not as claims that any backend already meets the compatibility contract.

| Option | Evidence and fit | Decision / unresolved checks |
| --- | --- | --- |
| Bundled libdxfrw | Already integrated in this fork and has version-specific read/write entrypoints; its static status matrices still require fixture and external-oracle gates (see the repo evidence above). | Keep as the in-tree baseline and close high-value DXF/DWG gaps incrementally. |
| ODA Drawings SDK | ODA advertises full DWG/DGN access, view/edit/create/save, PDF conversion, and publishes a supported-platform row for macOS arm64, Clang with macOS 11.0 SDK, static and dynamic libraries. Its page currently lists AC1032 through AutoCAD 2025; the Apple Silicon announcement dates to 2020. | Strongest native macOS SDK candidate to evaluate. Confirm current obtainable build, Qt 6/C++ toolchain and minimum macOS compatibility, signing/notarization and deployment packaging, annual membership and redistribution limits; prove AutoCAD 2027 files with the corpus. |
| LibreDWG | Upstream describes a C reader/writer and GPLv3-or-later licensing. Its current README says R2010–R2018 writing still produces CRC errors; AC1032 therefore is not a production-writer assumption. | Consider for read-only/import, diagnostics, or isolated experiments only until modern writing passes external validation. Review license and distribution questions with qualified counsel; this document makes no compatibility conclusion. |
| Autodesk RealDWG 2027 | Autodesk advertises source DWG/DXF read/write, but its 2027 requirements specify Windows 11 and Visual Studio 2026 with .NET 10. | Not a native macOS arm64 backend candidate under the published 2027 requirements. Revisit only if a separate Windows service is an intentional product architecture. |

ODA’s public page does document Apple Silicon support, so platform availability itself is no longer an open question. The exact package version and behavior in this Qt 6 application, Autodesk 2027 sample round-trips, deployment/signing, membership price, and distribution rights remain to be verified. Treat standalone conversion tools as useful for validation or migration, not substitutes for an in-process backend that preserves editable document semantics. [ODA Drawings SDK and supported-platform table](https://www.opendesign.com/products/drawings), [ODA Apple Silicon support announcement](https://www.opendesign.com/blog/2020/december/oda-releases-apple-silicon-support), [ODA Drawings SDK overview](https://www.opendesign.com/files/white-papers/ODA%20Drawings%20SDK.pdf), [ODA membership/products](https://www.opendesign.com/oda-membership), [ODA pricing and distribution terms](https://www.opendesign.com/pricing?language=en), [LibreDWG upstream README and license](https://github.com/LibreDWG/libredwg), [Autodesk RealDWG 2027 API and requirements](https://aps.autodesk.com/developer/overview/realdwg-api). Platform, version, and licensing facts above were checked against those vendor/project pages on 2026-10-11.

Do not let an SDK selection erase the compatibility gates above. Require the prototype to prove the same AC1032/DXF subset, no-loss behavior, layout/viewport semantics, PDF output, Apple Silicon performance, and supportable deployment. If no option meets the release bar, narrow the advertised DWG write contract while preserving DXF and DWG read-only support for proven subsets.
